# TaskFlow 框架建设待办

## 文档定位

本文档只关注工程框架和平台能力，不包含项目、任务、评论、附件、看板等业务功能实现。

目标是把当前“可以继续开发的工程骨架”提升为“适合多人协作和持续交付的工程平台”。

本文档不负责：

- Prisma 业务数据模型和种子数据。
- 注册、登录、JWT 和权限业务。
- 项目、任务、评论、附件和看板接口。
- 页面视觉设计和业务交互。

本文档负责：

- 仓库和包边界。
- 依赖、锁文件和版本治理。
- 根目录命令和本地开发。
- CI 质量门禁。
- 共享配置和接口契约基础设施。
- 后端运行时、错误、日志和可观测性基础。
- 测试分层、部署和依赖升级基础。

## 当前基线

当前已经具备：

- `apps/client` 和 `apps/server` workspace 包。
- pnpm workspace、唯一根锁文件和 Turborepo 任务图。
- 根目录 `pnpm dev` 联调启动脚本。
- 根目录统一的开发、构建、测试、类型检查、lint 和清理命令。
- 根目录 Prettier、cspell、Git hooks 和提交信息校验。
- 共享 TypeScript、ESLint、Vitest 配置包和 Zod 接口契约包。
- ESLint 静态检查和 GitHub Actions 最小质量门禁。
- 后端环境变量校验、健康检查、统一错误处理和 `requestId`。
- 前端 Vue、Vue Router、Pinia、Axios、Element Plus 基础入口。
- 中文需求、设计、原型、实施计划和进度文档。

当前主要缺口：

- 后端运行时缺少优雅停机、启动失败处理和监听地址配置。
- 日志仍是临时 `console.error`，没有结构化日志接口。
- 尚未建立单元、集成和端到端测试分层与覆盖率策略。
- 尚未建立部署、依赖升级和发布版本治理。

## 目标结构

建议保持单体仓库和前后端分离，不引入重型微服务或任务编排平台。

目标结构：

```text
TaskFlow/
├── pnpm-workspace.yaml
├── package.json
├── apps/
│   ├── client/
│   └── server/
└── packages/
    ├── config/
    └── contracts/
```

`packages/config` 用于共享 TypeScript、ESLint、Prettier、Vite 和 Vitest 配置。

`packages/contracts` 用于共享 API 类型、错误码和运行时 schema。建立前应先确定 OpenAPI 或 TypeScript schema 哪一个是唯一契约来源。

## P0：可复现和可验证

### F-01 建立 pnpm workspace（已完成，2026-09-24）

目标：

- 根目录、`client`、`server` 和未来的 `packages/*` 使用同一依赖图。
- 根目录维护唯一的 `pnpm-lock.yaml`。
- 不再保留 npm 或 Yarn 锁文件。

为什么现在做：

- 当前三个目录独立维护依赖和锁文件，安装方式、依赖解析和升级责任不统一。
- 根目录、前端和后端同时执行安装和脚本，CI 需要维护多套缓存和命令。
- 后续引入共享配置包或接口契约包时，没有 workspace 会继续复制配置和类型。

收益：

- 仓库只有一套锁文件和依赖图，安装结果更可复现。
- 根目录可以统一执行开发、测试、类型检查和构建命令。
- CI 缓存和依赖安装步骤更简单，新成员只需要执行一次根目录安装。

验收：

- 根目录执行 `pnpm install --frozen-lockfile` 可以安装全部依赖。
- 仓库中不存在 `package-lock.json`、`yarn.lock` 和子包独立锁文件。
- `pnpm -r` 可以发现所有 workspace 包。

### F-02 统一版本和包管理器约束（已完成，2026-09-24）

目标：

- 根目录和各包声明一致的 `packageManager`。
- 明确 Node.js 版本策略，建议当前使用 Node.js 20 或 22 LTS。
- 兼容的公共依赖尽量统一版本，避免同一工具在前后端使用不同主版本。

为什么现在做：

- Node.js 和 pnpm 主版本不同，会改变依赖解析、原生模块构建和锁文件格式。
- 当前本地版本、CI 计划和包声明并不完全一致，问题容易延迟到 CI 或部署时暴露。
- 前后端工具版本差距较大，新增依赖时很难判断应该跟随哪一套基线。

收益：

- 本地、CI 和生产构建使用一致的运行时和包管理器行为。
- 依赖升级和故障排查有明确基准，减少环境差异导致的问题。
- 后续新增 workspace 包时可以直接继承统一策略。

验收：

- 根目录、`client` 和 `server` 均有 `engines` 和 `packageManager`。
- 新增 `.nvmrc` 或 `.node-version`。
- CI 和本地使用相同 Node.js 与 pnpm 主版本。

### F-03 统一根目录命令（已完成，2026-09-24）

目标：

根目录至少提供：

```text
pnpm dev
pnpm build
pnpm test
pnpm typecheck
pnpm lint
pnpm format
pnpm format:check
pnpm clean
```

为什么现在做：

- 当前只有 `dev`、格式化和提交校验，开发者仍需记忆不同目录下的命令。
- CI 和本地验证如果没有统一入口，会逐渐出现“本地通过、CI 失败”或“CI 执行了另一套流程”。
- 后续 workspace 包增多后，逐个进入目录运行脚本会显著增加维护成本。

收益：

- 本地开发和 CI 使用同一组命令，降低认知负担。
- 新人只需要了解根目录命令即可开始工作。
- 更容易并行化测试和构建，也方便以后接入缓存或任务编排工具。

验收：

- 根目录命令可以调度对应 workspace 包。
- 单个服务仍可独立启动和测试。
- 根目录 `dev` 使用 workspace 并行能力或稳定进程管理方案。

### F-04 建立最小 CI（已完成，2026-09-24）

目标：

在 GitHub Actions 中建立统一质量门禁。

顺序：

```text
pnpm install --frozen-lockfile
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

为什么现在做：

- 当前质量检查全部可以在本地跳过，主干没有统一的合并门禁。
- 任务进入数据层、认证和业务接口后，回归成本会快速上升。
- 后续引入 workspace、共享配置和契约包时，需要 CI 验证迁移没有破坏构建。

收益：

- 每个 PR 都经过同一套格式、lint、类型、测试和构建检查。
- 错误在合并前被发现，降低主干不可用和返工成本。
- 重构和依赖升级有自动化安全网，可以更频繁地提交小变更。

验收：

- Pull Request 和主分支推送会触发 CI。
- CI 失败时不能合并。
- 测试需要数据库前，先使用无数据库测试；数据库接入后增加独立集成测试任务。

## P1：共享、运行时和质量基础

### F-05 建立共享配置包（已完成，2026-09-24）

目标：

- 抽取 TypeScript 基础配置。
- 抽取 ESLint、Prettier 和测试公共配置。
- 避免各包复制后逐渐分叉。

为什么现在做：

- 当前前端和后端各自维护 TypeScript 配置，未来还会增加 lint、测试和构建配置。
- 同一规则在多个包复制后，升级工具或修复规则时很容易漏改。
- 框架阶段先建立共享边界，比业务代码增多后再迁移成本低。

收益：

- 公共规则只有一个来源，修改一次即可作用于全部包。
- 前后端工具行为保持一致，减少“某个包通过、另一个包失败”。
- 新包可以直接继承配置，缩短脚手架搭建时间。

验收：

- `client` 和 `server` 通过 `packages/config` 继承配置。
- 修改公共规则只需要修改一处。

### F-06 确定接口契约来源（已完成，2026-09-24）

目标：

为前后端选择唯一的接口契约机制：

- OpenAPI 作为接口源，或
- `packages/contracts` 中的 TypeScript schema 作为接口源。

为什么现在做：

- 当前 API 契约主要存在于 Markdown 文档和后端实现中，前端无法自动保证一致。
- 错误码、响应结构、分页结构和字段类型一旦重复定义，就会在并行开发中漂移。
- 后续项目、任务、评论和附件接口会大量增加，越晚统一成本越高。

收益：

- 前后端基于同一契约开发，减少字段拼写和结构不一致问题。
- 契约变化可以触发类型检查或契约测试，而不是依赖人工比对。
- 后续可以生成客户端类型、SDK、Mock 或接口文档。

验收：

- 错误码、响应结构、分页结构和公共字段只保留一份定义。
- 前后端类型可以通过生成或直接引用保持一致。
- 契约变更必须伴随类型检查和测试。

### F-07 补齐后端运行时生命周期

目标：

- 监听地址由环境变量配置，默认开发使用 `127.0.0.1`。
- 支持 `SIGTERM` 和 `SIGINT` 优雅停机。
- 监听失败时输出明确错误并退出非零状态码。
- 预留数据库和外部资源关闭钩子。
- 区分 liveness 和 readiness。

为什么现在做：

- 容器平台通常发送 `SIGTERM` 后再强制结束进程，当前服务没有停机流程。
- 依赖数据库后，如果进程直接退出，连接、日志和未完成请求无法有序处理。
- readiness 和 liveness 不区分时，流量可能在依赖未就绪时进入实例。

收益：

- 发布和重启时减少请求中断、连接泄漏和数据不一致风险。
- 健康检查能表达真实服务状态，支持容器编排和负载均衡。
- 数据库和外部资源接入后可以直接挂接关闭钩子。

验收：

- 停止进程时先停止接收新请求，再关闭资源。
- 容器部署可以监听 `0.0.0.0`。
- 健康检查不只验证进程存在，还能表达依赖是否就绪。

### F-08 建立日志和错误分类基础

目标：

- 定义 Logger 接口，不在业务代码中直接使用 `console.error`。
- 结构化记录请求方法、路径、状态码、耗时和 `requestId`。
- 识别 body-parser、请求体过大、Multer 和 HTTP 客户端错误，避免误报 500。

为什么现在做：

- 当前错误日志依赖 `console.error`，格式不统一，无法直接用于检索和告警。
- 请求上下文已经生成 `requestId`，但没有形成完整的请求日志链路。
- 请求解析错误和文件错误如果不分类，会把客户端错误错误记录为服务端故障。

收益：

- 故障可以通过 `requestId` 串联请求、错误和后续日志。
- 错误状态码更准确，前端和测试可以稳定依赖错误契约。
- 后续接入日志平台、指标和 trace 时不需要重写业务代码。

验收：

- 开发和测试使用可读格式，生产使用 JSON 格式。
- 未知异常记录堆栈，但响应不泄露堆栈。
- malformed JSON、请求体过大和文件错误返回正确状态码。

### F-09 增加静态检查（已完成，2026-09-24）

目标：

引入 ESLint 或等效工具，覆盖 TypeScript 和 Vue。

重点规则：

- 未使用变量和导入。
- unsafe `any` 和类型断言。
- 浮空 Promise。
- Vue 组件和组合式 API 规范。
- 测试文件规范。

为什么现在做：

- TypeScript 类型检查不能发现所有语义问题，例如浮空 Promise 和危险断言。
- 只依赖人工评审会让质量取决于 reviewer 的注意力和经验。
- Vue 页面和业务模块增加后，再集中修复 lint 问题会产生大量无关改动。

收益：

- 常见错误在提交前自动拦截，降低运行时故障概率。
- 代码风格、异步处理和组件规则保持一致。
- 重构时可以依赖规则快速发现潜在影响面。

验收：

- 根目录存在 `pnpm lint`。
- CI 执行 lint。
- 新代码不能新增 lint error。

### F-10 测试分层

目标：

区分：

```text
unit
integration
e2e
```

为什么现在做：

- 数据层和外部依赖接入后，如果把所有测试混在一起，测试会越来越慢且不稳定。
- 单元测试、集成测试和端到端测试关注的失败原因不同，需要分开定位。
- 当前测试数量少，适合先建立目录和运行策略，而不是等测试规模变大后再拆分。

收益：

- 本地可以高频运行快速单元测试，CI 再运行完整测试集。
- 失败时更容易判断是业务逻辑、集成配置还是用户流程问题。
- 端到端测试只保留关键链路，降低维护成本和脆弱性。

验收：

- 单元测试不依赖数据库和网络。
- 集成测试可以使用独立测试数据库。
- 端到端测试在业务页面出现后运行。
- 覆盖率作为趋势指标，不在基础不稳定时设置过高门槛。

## P2：交付和长期维护

### F-11 建立部署基线

目标：

- 明确生产构建命令和生产启动命令。
- 提供 Dockerfile 或部署说明。
- 区分开发、测试和生产环境配置。

为什么现在做：

- 开发服务器不能代表生产运行方式，环境差异会导致部署时才发现问题。
- 当前配置、启动命令和构建产物还没有形成明确的部署契约。
- 后续依赖数据库、文件上传和外部服务后，部署步骤会继续增加。

收益：

- 构建产物可以在干净环境中重复部署。
- 开发、测试和生产配置边界清晰，降低密钥和配置误用风险。
- 发布、回滚和扩容有稳定基础。

验收：

- 不依赖开发服务器运行生产环境。
- 环境变量通过部署平台注入。
- 健康检查和停机行为符合部署平台要求。

### F-12 建立依赖升级策略

目标：

- 使用 Renovate 或 Dependabot。
- 对框架、构建工具和安全依赖设置升级策略。
- 大版本升级必须单独提交并验证。

为什么现在做：

- 依赖手动升级容易长期停滞，安全补丁也会被遗漏。
- 一次性跨多个主版本升级会放大迁移风险，难以定位问题。
- 框架依赖已经横跨多个主版本，需要建立稳定的升级节奏。

收益：

- 依赖升级拆分为小变更，持续降低技术债。
- 安全漏洞可以更快修复。
- 升级过程和验证结果有记录，便于回滚和复盘。

验收：

- 依赖更新有自动 PR。
- CI 自动验证依赖更新。
- 升级记录可以回溯。

### F-13 建立版本和发布约定

目标：

- 明确应用版本来源。
- 明确数据库迁移和发布顺序。
- 明确回滚策略。

为什么现在做：

- 没有版本和发布约定时，无法准确判断线上运行的是哪次代码。
- 数据库迁移和应用发布顺序错误，会造成不可逆的数据问题。
- 回滚如果依赖临时判断，会延长故障恢复时间。

收益：

- 代码、构建产物和发布记录可以相互追踪。
- 迁移、发布和回滚可以按固定流程执行。
- 故障复盘时可以准确定位变更范围和责任边界。

验收：

- 构建产物包含可追踪版本。
- 发布说明关联提交和迁移。
- 失败时存在可执行回滚路径。

### F-14 自动化进度和仓库状态

目标：

- 提交号、分支和远端同步状态尽量自动生成。
- 人工进度文档只记录决策、风险和下一阶段。

为什么现在做：

- 当前进度文档手工记录提交号和远端状态，已经容易在提交后立即失真。
- 提交状态属于机器可生成信息，人工维护会持续消耗注意力。
- 恢复文档真正需要保留的是决策、风险和下一步，不是重复 Git 信息。

收益：

- 新会话恢复时减少过期信息干扰。
- 文档更新成本更低，内容更聚焦架构决策。
- 仓库状态可以通过脚本稳定生成。

验收：

- 文档不会因提交变化快速失真。
- 新会话可以稳定恢复上下文。

## 推荐实施顺序

1. F-01、F-02：统一 workspace、锁文件和版本策略。
2. F-03：建立统一根目录命令。
3. F-04：建立最小 CI。
4. F-05、F-06：共享配置和接口契约基础。
5. F-07、F-08：运行时生命周期、错误分类和日志接口。
6. F-10：测试分层。
7. F-11 至 F-14：部署、升级和发布治理。

## 暂不引入

当前规模不需要：

- 微服务拆分。
- Nx 和远程构建缓存。
- CQRS、事件溯源和消息总线。
- 多仓库和独立发布流水线。
- 为业务功能提前建立复杂抽象。

## 框架完成标准

- 根目录一次 `pnpm install --frozen-lockfile` 可以安装全部依赖。
- 仓库只保留一套锁文件。
- 根目录具备统一开发、构建、测试、类型检查、lint 和清理命令。
- CI 覆盖格式、lint、类型、测试和构建。
- 前后端共享配置和接口契约边界明确。
- 后端具备优雅停机、正确错误分类和结构化日志接口。
- 新成员可以按照 README 独立完成首次启动和验证。
