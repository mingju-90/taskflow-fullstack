# TaskFlow 产品需求

## 1. 产品概述

TaskFlow 是一个面向小型协作场景的任务管理应用。用户可以在项目中组织成员、创建和分配任务、更新任务状态、讨论任务并上传相关附件。第一版的产品重点不是覆盖完整的企业协作能力，而是提供一条可以独立运行、完整解释和自动化验收的全栈链路。

## 2. 产品目标

### 2.1 用户目标

- 用户可以快速注册、登录并恢复自己的登录状态。
- 用户可以创建项目并邀请已注册用户参与。
- 用户可以按项目集中查看、筛选和管理任务。
- 用户可以围绕任务进行评论和附件协作。
- 用户可以在看板快速了解自己的任务数量和近期项目。

### 2.2 学习目标

- 理解浏览器、Vue、HTTP、Express、Service、Prisma 和 SQLite 之间的调用链。
- 理解认证与授权的区别，以及项目级权限如何在服务端执行。
- 理解关系建模、事务、联表查询、文件生命周期和统一错误处理。
- 理解单元测试、API 集成测试和端到端测试分别解决什么问题。
- 通过持续集成把类型检查、构建和测试变成稳定门禁。

### 2.3 产品成功标准

- 新用户可以按照 README 从零启动前后端。
- 一条完整用户链路可以注册、创建项目、创建任务、评论、修改状态并退出。
- 未登录、越权、非法输入和文件错误都得到稳定且可理解的响应。
- 关键业务规则同时有自动化测试和可追踪验收项。
- 核心页面在 1440 x 900 和 1920 x 1080 桌面视口下信息完整且无重叠。

## 3. 用户角色

| 角色          | 定义                       | 核心能力                                             |
| ------------- | -------------------------- | ---------------------------------------------------- |
| 访客          | 未登录用户                 | 注册、登录                                           |
| 已登录用户    | 已通过 JWT 验证的用户      | 查看个人看板、创建项目、访问自己所属项目             |
| 项目 `MEMBER` | 已被加入项目的普通成员     | 查看项目、创建和编辑任务、评论、上传附件             |
| 项目 `OWNER`  | 项目创建者，每个项目仅一人 | 拥有 `MEMBER` 全部能力，并可管理项目、成员及删除项目 |

第一版不提供自定义角色、组织管理员或跨项目超级管理员。

## 4. 范围

### 4.1 第一版包含

- 用户名、邮箱和密码注册。
- 邮箱和密码登录。
- JWT 鉴权、当前用户恢复和前端退出。
- 项目创建、编辑、删除和项目列表。
- 通过邮箱或用户名添加已注册成员。
- 项目成员移除，项目负责人不可移除。
- 任务创建、查看、编辑、删除、筛选和分页。
- 负责人分配和截止时间。
- 任务评论的新增、查看和删除。
- PDF、PNG、JPEG、纯文本附件上传、下载和删除。
- 个人看板统计和最近项目。
- 桌面端响应式布局、加载态、空态、错误态和操作反馈。

### 4.2 第一版不包含

- 邮箱验证、找回密码、第三方登录和账号删除。
- Refresh Token、Cookie 会话和完整设备管理。
- 多组织、多租户、自定义角色和权限配置。
- 实时通知、WebSocket、消息队列和后台任务。
- 对象存储、CDN、云部署和容器编排。
- 软删除、回收站、数据导出和恢复。
- 自定义任务状态、工作流、甘特图和图表库。
- 移动端专用交互。第一版仍保证窄屏不出现核心内容重叠，但不承诺完整移动办公体验。

## 6. 核心场景

### 场景 A：从注册到第一个任务

1. 访客注册账号。
2. 注册成功后进入登录状态或跳到登录页。
3. 用户创建项目并成为 `OWNER`。
4. 用户进入项目并创建第一个任务。
5. 用户在项目任务列表和任务详情中看到一致的数据。

### 场景 B：多人协作

1. `OWNER` 通过邮箱或用户名添加已注册用户。
2. 新成员进入项目，查看任务和评论。
3. 成员创建任务并分配负责人。
4. 成员修改任务状态、发表评论并上传附件。
5. 只有符合规则的作者、任务创建人或 `OWNER` 才能执行受限删除操作。

### 场景 C：受限访问

1. 未登录用户访问受保护页面时被引导到登录页。
2. 非项目成员访问项目、任务、评论或附件时被后端拒绝。
3. 普通成员尝试管理成员或删除他人任务时收到明确反馈。
4. 前端不展示无权操作按钮，但后端仍执行最终授权。

### 场景 D：自动化验收

1. 每次推送或合并请求触发类型检查、单元测试、集成测试和构建。
2. 端到端任务启动真实前端和后端，执行核心冒烟流程。
3. 任一门禁失败时，持续集成结果失败，不得合并或发布。

## 7. 体验原则

- 信息优先：项目和任务列表要便于扫描，不使用营销式首屏或大面积装饰。
- 操作可发现：主操作使用明确的文字按钮，高频工具栏可使用带提示的图标。
- 状态完整：每个数据页面覆盖加载中、空状态、错误重试和成功反馈。
- 权限清晰：无权操作不展示；后端拒绝时提供可理解的错误消息。
- 数据一致：表单提交后以服务端返回数据刷新页面状态。
- 桌面优先：核心操作在 1440 x 900 下无需横向滚动，1920 x 1080 下内容不空洞拉伸。

## 8. 假设与约束

- 用户使用现代桌面浏览器，默认支持 Chromium。
- 第一版运行于本地环境，前后端分别启动，不使用 npm workspace。
- 所有日期以 ISO 8601 字符串传输，前端按用户本地时区展示。
- 所有业务数据都通过 `/api/v1` 访问。
- `OWNER` 和 `MEMBER` 是固定项目角色，不提供多负责人。
- JWT 保存在 `localStorage` 仅用于练手，文档必须说明生产环境风险。
